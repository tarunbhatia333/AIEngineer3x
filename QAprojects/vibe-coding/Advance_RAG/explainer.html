01 · Why upgrade at all

A basic RAG answers. This one shows its work.

A minimal RAG demo embeds text, searches a vector store, and asks an LLM to answer. That works until your corpus stops being three sample paragraphs — at real scale (thousands of QA test cases with IDs, priorities, JIRA links) the gaps show up fast: keyword-exact queries miss semantically-phrased chunks and vice versa, the top match isn't always the best match, and one phrasing of a question can miss chunks a slightly different phrasing would have found.

Why the overlap matters

Most test cases here are short enough to stay as a single chunk. When one doesn't fit, splitting it blind would risk cutting "3. Click Publish" from its own expected result on the next chunk. The 150-character overlap means both halves keep enough of the boundary sentence to stand alone as a retrieval unit.

03 · The core idea

Two rankings almost never agree — that disagreement is the signal

A dense embedding finds chunks that mean the same thing as the query, even with zero shared words. A sparse TF-IDF vector finds chunks that share the query's exact vocabulary — a JIRA ID, an error string, a UI label — which dense embeddings routinely blur together. Neither ranking is "the" ranking. Reciprocal Rank Fusion combines them without needing their scores to be on the same scale: it only looks at each list's rank order.

RRF(chunk) = Σ 1 / (k + rank)
summed over every ranked list the chunk appears in · k = 60 in this build

Worked example

Two chunks, two rankings. Chunk A wins on meaning; Chunk B wins on wording — and also shows up, second-best, on meaning. Fusion rewards the chunk both signals partially agree on:

Chunk A
dense rank1st
sparse rank3rd
RRF = 1/61 + 1/63 = 0.0323
Chunk B
dense rank2nd
sparse rank1st
RRF = 1/62 + 1/61 = 0.0325

Chunk B edges ahead — despite never being the single best match on either signal alone. In vectorstore.py, rrf_fuse() does exactly this over as many ranked lists as you hand it, which matters for the next section.

Why Chroma changes the sparse half. Qdrant stores native sparse vectors alongside dense ones in the same point. OSS Chroma doesn't — so sparse_index.py hand-rolls a small TF-IDF inverted index that lives beside the Chroma collection and gets queried in parallel. Same fusion math, different plumbing underneath.

05 · An honest tradeoff

Two model profiles behind one interface

The original spec called for bge-m3 (2.3GB) and bge-reranker-v2-m3 (570MB). Those are real, and wired up — but they're not the default, because a demo that takes ten minutes to cold-start on a laptop teaches worse than one that runs immediately.

ProfileDense embedderRerankerFootprint
light defaultBAAI/bge-small-en-v1.5ms-marco-MiniLM-L-6-v2~220MB
fullBAAI/bge-m3BAAI/bge-reranker-v2-m3~2.9GB

Both profiles implement the exact same .encode() / .score() interface (embeddings.py, reranker.py), so switching is one line in .env: MODEL_PROFILE=full.

07 · Before you share this anywhere

One thing worth fixing before this repo goes further

keys_private.md, sitting beside this file, holds live plaintext API keys (Pinecone, OpenAI ×2, Groq, Vercel). It wasn't tracked by git when this project was built, and .gitignore now excludes it and .env explicitly — but a plaintext key file in a project folder is exactly the kind of thing that gets swept up by a future git add -A. Worth moving those keys into a password manager and rotating the ones that have ever been pasted into a chat, an issue, or a doc.
